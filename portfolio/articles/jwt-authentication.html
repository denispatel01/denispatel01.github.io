JWT Authentication & Role-Based Authorization

JWT (JSON Web Token) is the standard way to secure a stateless REST API. The idea is simple, but the details are where security lives. Here's the model I use to secure ASP.NET Core APIs — and the mistakes that quietly break it.

What a JWT actually is

A JWT is three base64url parts separated by dots: header.payload.signature.

  • Header — the signing algorithm (e.g. HS256 or RS256).
  • Payload — the claims: who the user is, their roles, expiry (exp), and so on. This is not encrypted — anyone can read it. Never put secrets here.
  • Signature — a cryptographic signature over the header and payload. This is what makes the token tamper-proof: change one byte of the payload and the signature no longer validates.

Key mental model

A JWT is not secret — it's trusted. The server doesn't store sessions; it re-verifies the signature on every request. Valid signature + not expired = the claims can be trusted.

The flow

  1. User logs in with credentials.
  2. Server verifies them and issues a signed JWT containing the user's id and roles.
  3. Client sends the token on every request: Authorization: Bearer <token>.
  4. Server validates the signature and expiry, then authorizes based on the claims.

Securing an ASP.NET Core API

// Program.cs — register JWT bearer authentication
builder.Services
  .AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
  .AddJwtBearer(options =>
  {
      options.TokenValidationParameters = new TokenValidationParameters
      {
          ValidateIssuer = true,
          ValidateAudience = true,
          ValidateLifetime = true,          // reject expired tokens
          ValidateIssuerSigningKey = true,  // verify the signature
          ValidIssuer = cfg["Jwt:Issuer"],
          ValidAudience = cfg["Jwt:Audience"],
          IssuerSigningKey = new SymmetricSecurityKey(
              Encoding.UTF8.GetBytes(cfg["Jwt:Key"]))
      };
  });

app.UseAuthentication();
app.UseAuthorization();

Role-based authorization

Once roles are claims in the token, protecting an endpoint is declarative:

[Authorize(Roles = "Admin,Registrar")]
[HttpPost("admissions")]
public IActionResult CreateAdmission(AdmissionDto dto) { ... }

Common mistakes that break "secured"

  • Putting secrets in the payload. It's readable by anyone. Claims are for identity and roles, not passwords or PII.
  • Not validating lifetime. Skipping ValidateLifetime means expired tokens live forever.
  • Long-lived tokens with no refresh strategy. Use short-lived access tokens plus a refresh-token flow so a stolen token has a small blast radius.
  • Weak or committed signing keys. The key must be long, random, and stored in configuration/secrets — never in source control.
  • Trusting client-supplied identifiers. Authorize on claims from the verified token, not on ids in the request body.

This is the model securing the Nucleus EDU API across 10+ modules, and the borrower-verification flows in the nVizion loan platform.
