Multi-Tenant Architecture in ASP.NET Core

"Multi-tenant" means one application instance serves many isolated customers (tenants). The hard question isn't the code — it's where you draw the isolation boundary. Get it wrong and you either leak data between tenants or drown in maintenance. Here's how I think about it, and what I shipped for a multi-campus school ERP.

Three isolation models

There are three common approaches, from least to most isolated:

  1. Shared database, shared schema — every table has a TenantId column and every query filters on it. Cheapest to run, but one missing filter leaks data, and a heavy tenant slows everyone.
  2. Shared database, separate schema — each tenant gets its own schema. Cleaner separation, but migrations multiply.
  3. Database per tenant — each tenant has its own database. Strongest isolation, easy per-tenant backup/restore, and no cross-tenant query risk. The trade-off is managing more databases.
For a school ERP where each campus holds sensitive student data, isolation wins. I chose database-per-tenant with per-request connection resolution.

The core idea: resolve the connection per request

Instead of one deployment per campus, a single deployment figures out which database to talk to based on the authenticated tenant on each request. The tenant comes from a trusted source — typically a claim in the JWT — never from user input. 

// 1) Resolve the current tenant from the request (JWT claim)
public class TenantContext
{
    public string TenantId { get; }
    public TenantContext(IHttpContextAccessor http)
    {
        TenantId = http.HttpContext?.User
            .FindFirst("tenant")?.Value
            ?? throw new UnauthorizedAccessException("No tenant.");
    }
}

// 2) Map tenant -> connection string (from config, not hard-coded)
public string ResolveConnection(string tenantId) =>
    _config.GetSection($"Tenants:{tenantId}:ConnectionString").Value
        ?? throw new InvalidOperationException($"Unknown tenant {tenantId}");

// 3) Configure EF Core to use the resolved connection
services.AddDbContext<AppDbContext>((sp, options) =>
{
    var tenant = sp.GetRequiredService<TenantContext>();
    var cs = sp.GetRequiredService<ITenantStore>().ResolveConnection(tenant.TenantId);
    options.UseSqlServer(cs);
});

The golden rule

The tenant identifier must come from a trusted, server-verified source (a signed JWT claim), never from a query string or header the client can set. Otherwise multi-tenancy becomes a data-leak vulnerability.

Configuration over hard-coding

Connection strings live in environment-driven configuration, not in code. That's what lets the same build run in Dev, Staging, UAT, and Production, and lets you add a new campus by adding config — not by redeploying.

What you get

  • Strong data isolation — no cross-tenant query can accidentally return another campus's rows.
  • Per-tenant operations — back up, restore, or migrate one campus without touching the others.
  • One codebase, one deployment — the maintenance win that makes multi-tenancy worth it.

This is exactly the architecture behind Nucleus EDU, which serves 2,200+ users across multiple campuses from a single API deployment.
