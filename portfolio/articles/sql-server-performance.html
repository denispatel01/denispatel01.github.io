Performance

Making Slow SQL Server Screens Fast

When a platform grows past a couple thousand users, the screens that felt instant on day one start to crawl. Almost always, the fix isn't a bigger server — it's better data access. This is the playbook I used to keep a 2,000+ user platform responsive.

1. Measure before you touch anything

Guessing at performance wastes time. I start with SQL Profiler (or Extended Events) to capture the actual slow queries and their duration, reads, and frequency. The worst offender is usually a query that's both slow and called constantly. Then I read the actual execution plan to see where time goes.

Optimize the query that costs the most × runs the most — not the one that looks ugliest.

2. Index to match real query patterns

The classic symptom is a table scan where you expected a seek. Indexes should match how the data is actually filtered and sorted. A covering index that includes the columns a query selects can eliminate expensive key lookups entirely. 

-- Filtered + sorted by these columns on a hot query? Index them.
CREATE NONCLUSTERED INDEX IX_Attendance_Student_Date
  ON Attendance (StudentId, [Date])
  INCLUDE (Status);   -- covering: no key lookup needed

Caveat

Indexes speed reads but slow writes and use space. Add them deliberately, based on measured query patterns — not one per column "just in case".

3. Rewrite the stored procedures that hurt

Common wins when rewriting SPs:

  • Replace correlated subqueries and row-by-row logic with set-based joins.
  • Eliminate redundant scans of the same table.
  • Avoid functions on indexed columns in WHERE clauses (they defeat the index).
  • Watch for parameter sniffing on procs that behave well for one input and badly for another.

4. Never fetch what you won't show: server-side pagination

The single biggest win on list-heavy screens. Instead of pulling thousands of rows to the app and paging in memory, fetch exactly one page from the database: 

SELECT StudentId, Name, GradeName
FROM   Students
WHERE  CampusId = @CampusId
ORDER  BY Name
OFFSET     @PageSize * (@PageNumber - 1) ROWS
FETCH NEXT @PageSize ROWS ONLY;

Combined with a matching index on the ORDER BY column, this keeps a grid fast whether the table has 1,000 rows or 1,000,000.

The results

On Nucleus EDU, applying exactly these steps — profile, index, rewrite SPs, paginate — kept the high-volume modules responsive as daily usage scaled past 2,000 users, with no infrastructure upgrade.
